# Oops Dance Studio — API contract (v1.25)

The single source of truth for the API between the backend (`supabase/`) and the frontend (`frontend/`): schema, roles, row-level security, RPC functions, the Edge Function, Storage, scheduled jobs, auth and environment.
- Any change to the backend's behaviour is written back into this file and logged in the Changelog at the bottom.
- How each call of the legacy frontend maps onto this API is in [frontend-mapping.md](frontend-mapping.md).

---

## 0. Ground rules

- The legacy Django backend (`oops-dance_be`) was a read-only reference for the business rules. It is not part of this repository.
- The old GitHub repos (`cookingminh/oops-dance_be`, `cookingminh/oops-dance_fe`) have a leaked secret in their history and are abandoned. **Never push to them.** This monorepo starts with a fresh history.
- No secrets in git. `.env*` is gitignored and only `.env.example` gets committed. The service-role / secret key is **never** used in the frontend.
- Studio timezone is `Asia/Ho_Chi_Minh`. "Today" is always computed with `public.studio_today()`, never the client clock.
- Money is VND, stored as `numeric(12,0)`.
- **Weekday convention is ISO: 1 = Monday … 7 = Sunday** (`extract(isodow from d)`). Legacy Django used `'0'` = Monday, and its room-availability code had a bug that mixed `%w` (Sunday = 0) with Monday = 0. Do not reproduce it.
- This is a new app with a fresh database: **no data is imported** from the legacy MySQL database.
- Times are Postgres `time`. PostgREST returns them as `"HH:MM:SS"`; RPC arguments accept `"HH:MM"` or `"HH:MM:SS"`.
- Cloudinary is gone for good and no backup of it exists. No Cloudinary code, URL or env var anywhere. The only legacy images used are the instructor/class photos in `scripts/demo-assets/` (WebP, committed) and the room photos in `frontend/src/assets/images/`; `scripts/demo-images.mjs` uploads them for the demo (§11). Every image path may still be `null` / empty; the UI renders a fallback.

## 2. Roles

`enum app_role: admin | staff | instructor | guest` (guest = student/customer)

- Each auth user has exactly one `public.profiles` row. A trigger on `auth.users` insert creates it.
  - The role is **always `guest`** at sign-up, whatever the client sends.
  - Only `username, full_name, contact_number, date_of_birth` are read from `raw_user_meta_data`. Empty strings become `null`; a malformed `date_of_birth` is ignored (stored as `null`) instead of failing sign-up.
  - A taken `username` makes sign-up fail with GoTrue's generic `Database error saving new user`. Check first with `is_username_available` (§5).
- `auth.users.email` changes are mirrored into `profiles.email` by a trigger.
- Only admins change roles, through `admin_set_role`. A trigger on `profiles` blocks changes to `role` and `email` (and `id`) unless `is_admin()` is true or the call comes from a **service context** (service-role key, migrations/seed, pg_cron, GoTrue itself). Violations raise `FORBIDDEN: …`.
- Invariants enforced by the same trigger on every write path (`INVALID_STATE: …`):
  - the last admin cannot be demoted;
  - an instructor who still teaches classes cannot change role (reassign the classes first).
- Helpers are `security definer`, `stable`, with `set search_path = ''`:
  - `public.current_app_role()`
  - `public.is_admin()`
  - `public.is_staff()`, which is true for admin **or** staff
  - Executable by `authenticated` (they back the RLS policies); `anon` gets permission denied.
- Admin vs staff:
  - Staff runs day-to-day operations: rooms, classes, bookings, attendance.
  - Admin can do everything staff can, plus user management, role changes, and hard deletes of users.
- Internal trigger functions and helpers live in schema `private`, which the Data API does not expose.

## 3. Tables (`public`)

All `id bigint` columns are `generated by default as identity`.

**profiles**
- `id uuid pk references auth.users on delete cascade`
- `email text not null` (synced from auth.users by trigger; read-only for everyone but admin/service)
- `username text unique`
- `full_name text not null default ''`
- `role app_role not null default 'guest'`
- `date_of_birth date`
- `contact_number text`
- `avatar_path text` (path in bucket `avatars`)
- `created_at`, `updated_at`

**rooms**
- `id bigint identity pk`
- `name text unique not null`
- `size text`
- `price numeric(12,0) not null check (price >= 0)` — VND **per hour** (used by `create_booking`)
- `image_paths text[] not null default '{}'` — room photos in bucket `site-assets` at `rooms/{room_id}/{file}`, in display order (first = cover); no `null` elements. Readable by anon like the rest of `rooms`; staff edit it.
- `created_at`, `updated_at`

**classes**
- `id bigint identity pk`
- `name text unique not null` (legacy name: `class_name`)
- `instructor_id uuid not null references profiles`. A trigger enforces that this profile has role instructor (`INVALID_INPUT: …` otherwise).
- `room_id bigint references rooms on delete set null`. Moving a class to a room re-checks all its schedules there (same rules as `class_schedules`, `SLOT_TAKEN: …`).
- `price numeric(12,0) not null check (price >= 0)`
- `lesson text` (legacy name: `class_lesson`): the title of the class's **latest** `class_lessons` row, kept in sync by a trigger. Clients do not write it.
- `image_path text` (bucket `class-images`)
- `level text` (migration `20261117001500_timetable_templates.sql`): `newbie | basic | advanced` (`check`), null = not set. The website's poster timetable colours each class by it (Newbie red, Basic brown, Advanced yellow, as on the studio's printed schedule) and keys the colours under the grid; a class without one is grey. Written like the rest of a class (staff, the class forms).
- How its pictures are framed on the website (migration `20261117001600_timetable_photos.sql`), set by staff with a live preview (the class page's Setup tab) and written like the rest of a class:
  - `image_pos_x`, `image_pos_y smallint not null default 50` (`check` 0–100): which part of `image_path` the website's class card shows — CSS `object-position` in % (the card is a 16 : 10 crop of a tall poster; a larger y shows more of its lower part). The app's other crops of the image follow it.
  - `timetable_photo_path text` (≤ 300; bucket `class-images`, `{class_id}/{uuid}.{ext}` like the image): the class's own round photo on the poster timetable, often a cut-out of the instructor (one instructor can look different per class); null = the instructor's avatar. Replacing or removing it deletes the old file; removing also resets the frame. Deleting the class deletes both files.
  - `timetable_photo_x`, `timetable_photo_y smallint not null default 50` (0–100), `timetable_photo_zoom smallint not null default 100` (50–300): its frame — the photo's point (x %, y %) sits in the middle of the circle and the photo is zoom % of the circle wide (its height follows its aspect). The avatar fallback ignores it (the app frames avatars on the head and shoulders).
- `created_at`, `updated_at`

**class_schedules** is one-to-many and replaces the legacy shared many-to-many `ClassSchedule`.
- `id bigint identity pk`
- `class_id bigint not null references classes on delete cascade`
- `day_of_week smallint not null check (day_of_week between 1 and 7)`
- `start_time time not null`, `end_time time not null`, `check (end_time > start_time)`
- `unique (class_id, day_of_week, start_time)`
- **Trigger** `check_class_schedule_slot` (insert/update), `SLOT_TAKEN: …` when the schedule, in its class's room on that weekday, overlaps
  - another schedule of any class (including the same class), or
  - a `pending`/`approved` booking dated today or later.
  - Back-to-back is fine (18:00–19:30 then 19:30–21:00). A class without a room blocks nothing.

**Rented studios (venues)** (migration `20261117001300_venues.sql`): while the studio's own rooms are closed, classes are taught in studios rented by the hour. The rooms and everything about them (bookings, clashes, prices) stay for when the studio reopens.
- `venues`: `name` (unique, 1–100), `address?` (≤ 200), `map_url?` (https, ≤ 500), `rent_per_hour` (≥ 0, what the studio pays), `note?` (≤ 300), `active`, timestamps. Anyone (anon too) may read `id, name, address, map_url, active, created_at, updated_at`; `rent_per_hour` and `note` are column-revoked (staff read them with `venues_list()`), so never `select=*` on it. Writes only through the RPCs (§5).
- Where a class is taught: `classes.room_id` (one of the rooms) **or** `classes.venue_id` (→ venues, `set null`), never both (`classes_one_place`). Sessions carry their own place the same way (`instructor_attendance.room_id` / `venue_id`, `instructor_attendance_one_place`): a new session without one takes its class's venue (trigger `session_place`; the room is copied by whoever inserts it); changing a class's place moves its sessions not started yet (`class_place_changed`). Room clash rules only concern rooms.
- The rent is a cost: once a session at a venue has ended and wasn't called off, it becomes an expense (`category 'venue_rent'`, `rent_per_hour × the session's length` rounded to 1,000 ₫, `class_id`, `session_id` → instructor_attendance (unique, `set null`), `vendor` = the venue's name, `description` 'Studio rent: {class}, HH:MM–HH:MM', `created_by` null, not logged). Calling the session off afterwards deletes it. The daily job (§8) and `venue_rent_run()` charge the last 60 days.

**Class lifecycle** (migration `20261114000100_class_lifecycle.sql`): `classes.starts_on date` (default today; an upcoming class takes students now and bills from its first month, no sessions before it), `ended_on date` (null = running; the last day), `end_reason`, `final_schedule jsonb` (the weekly sessions, kept once ended). After the last day the daily job (§8) stores the schedule in `final_schedule`, deletes the schedule rows (the room is free, no more sessions or timetable entries) and removes the students; history stays. Ended classes are left out of `list_public_classes()`. A class with completed sessions, marked roll calls or money paid cannot be deleted (`IN_USE: … end it instead`).

**class_lessons** holds the *routines*: the piece (song) a class learns over a number of sessions (migration `20261115000100_routines.sql`; originally one per month).
- `id bigint identity pk`
- `class_id bigint not null references classes on delete cascade`
- `month date not null`, the first day of the month (`check (month = date_trunc('month', month))`)
- `title text not null`, 1–120 characters after trimming (e.g. `Super Shy — NewJeans`)
- `starts_on date not null` (when the routine starts) and `session_count smallint` (1–60, default 8); `month` is kept and always set to the first day of `starts_on`'s month; `unique (class_id, starts_on)` replaces one-per-month. `classes.lesson` mirrors the *current* routine (latest started, else the next), refreshed daily.
- **One routine at a time** (trigger `routine_order`, migration `20261117000100_routine_order_and_waive.sql`): when a signed-in person inserts a routine or changes its `starts_on` / `session_count`, it must start after the projected last session of the routine before it, and end before the next one starts; otherwise `INVALID_STATE: routine order: …`. Seeds and jobs aren't checked. A session cancelled later can still push a routine past the next start; the Routines tab flags that overlap.
- `video_url text` (nullable): the class's end-of-month video of that piece. Only YouTube video links are accepted (`check class_lessons_video_url_youtube`: `https://` + `youtube.com/watch?v=`, `/shorts/`, `/embed/`, `/live/` or `youtu.be/`, then an 11-character id). Same RLS as the row (public read, staff write). The public /classes page shows the videos of the latest finished month that has any (normally last month); videos added to the running month wait until it ends.
- **Promo** (migration `20261117000700_routine_promos.sql`): before a routine starts, its class's instructor films a short clip of it so students know what they'd learn if they continue and visitors see what's coming. Either an uploaded clip — `promo_path text` (bucket `class-promos`, `{class_id}/{lesson_id}/{name}.{mp4|mov|webm}`, checked against the row's own class and id) with `promo_poster_path text?` (`….{jpg|webp}`, needs `promo_path`) and `promo_seconds smallint?` (1–180) — or `promo_url text` (a YouTube link, Shorts included; same rule as `video_url`), never both (`class_lessons_promo_one`). `promo_caption text?` (1–200, the line for students), `promo_by uuid?` (→ profiles, `set null`), `promo_at timestamptz?`; all null when there is no promo. Public read like the row; written through `lesson_set_promo` (§5), which lets the class's instructor in. Shown to the class's students (class page, renewal), on /classes ("Coming next": per class the next routine's promo, else the one started in the last 7 days) and in the staff to-do list (a routine starting within 14 days without one).
- `unique (class_id, month)`: save a month again with `upsert … on conflict (class_id, month)`
- `created_at`, `updated_at`
- **Trigger** `sync_class_lesson` (insert/update/delete) sets `classes.lesson` to the title of the latest month, or `null` when none is left.
- A class with no row for the current month keeps showing its latest lesson; the admin UI flags it as "needs this month's lesson" and lists it in the staff to-do list.

**Payroll** (admin only; migration `20261110000100_payroll.sql`)
- `payroll_settings`: one row (`id = 1`), `default_session_rate numeric(12,0)` (300,000 VND).
- `class_pay_rates (class_id pk → classes on delete cascade, session_rate)`: a class's own rate. Kept out of
  `classes` because classes are publicly readable.
- `staff_salaries (profile_id pk → profiles on delete cascade, monthly_salary)`: fixed monthly pay (office staff, or
  an admin who is paid).
- `payroll_adjustments (id, profile_id, month, amount, reason, attendance_id?, created_by, created_at)`: `month` is the
  first day of the month, `amount <> 0` (> 0 bonus, < 0 deduction), `reason` 1–200 characters; `attendance_id`
  optionally points at the session it is about (e.g. a late check-in).
- `payslips (profile_id, month) pk`: the frozen numbers of a finalized month — `sessions`, `session_pay`,
  `base_salary`, `bonuses`, `deductions` (≤ 0), `total`, `status` `finalized | paid`, `finalized_at/by`, `paid_at`.
  No row = the month is a live draft.
- **Pay rules**: an instructor earns one session for every `instructor_attendance` row of the month with status
  `completed` (checked in and out with proofs, or marked completed by staff), at the class rate or the default rate;
  `cancelled` and still-open sessions earn nothing. Total = session pay + monthly salary + bonuses + deductions.
- **Trigger** `guard_finalized_adjustments`: a month with a payslip can't get, change or lose adjustments
  (`INVALID_STATE: …`) until it is reopened.

**class_students**
- `class_id bigint references classes on delete cascade`
- `student_id uuid references profiles on delete cascade`
- `joined_at date not null default studio_today()`
- `primary key (class_id, student_id)`

**bookings**
- `id bigint identity pk`
- `room_id bigint not null references rooms` (no cascade: a room with bookings cannot be deleted → `23503`)
- `guest_id uuid not null references profiles` (no cascade: a user with bookings cannot be deleted)
- `date date not null`
- `start_time time not null`, `end_time time not null` (legacy names: `checkin_time` / `checkout_time`)
  - Must satisfy `end > start` (`bookings_time_order`), fall within 08:00–22:00 (`bookings_opening_hours`) and sit on the **30-minute grid**: `HH:00` or `HH:30` (`bookings_half_hour_grid`).
- `status booking_status not null default 'pending'`, where `booking_status` = `pending | approved | rejected | cancelled | completed` (replaces the legacy `BookingStatus` table)
- **Paid in full = completed** (migration `20261117001000_booking_auto_complete.sql`, trigger `booking_auto_complete`): an `approved` booking becomes `completed` by itself once `bank_transfer + cash ≥ full_payment`; money taken back before its day makes it `approved` again; staff can still mark a past booking completed by hand. A `completed` booking ahead holds its room like an approved one (free slots, booking rules, make-up and timetable clashes, reopening a session); the overlap constraint still covers pending / approved only, `check_booking_rules` checks completed ones ahead. It can still be cancelled (`cancel_booking`) before it starts.
- `deposit`, `full_payment`, `real_income`, `bank_transfer`, `cash`: all `numeric(12,0)` nullable, `check (>= 0)`
- `deposit_status deposit_status not null default 'waiting'`, where `deposit_status` = `waiting | completed | cancelled`
- **Cancellation and refund** (migration `20261117000800_booking_refunds.sql`): `cancelled_at`, `cancelled_by`, `cancel_kind` (`guest` | `studio`), `refund_due` (money still to give back, ≥ 0), `refund_paid` (given back), `refund_to` (where the guest wants it, ≤ 200), `refund_note` (≤ 300), `refunded_at`. On a cancellation `real_income` becomes what the studio keeps (paid − refund), so revenue (`v_revenue_monthly`, `dashboard_stats`, `finance_monthly`) now counts `cancelled` bookings too. Trigger `booking_status_money`: a plain status change to `rejected` / `cancelled` (the staff form) makes everything received due back (`cancel_kind` studio); changing it back clears the cancellation and the refund.
- `booking_settings` (one row, id 1; everyone reads, admins change through `booking_set_refund_policy`): `refund_full_hours` (null = no full-refund step; else more than the partial hours), `refund_partial_hours` (default 24), `refund_partial_percent` (default 50). Cancelling at least `refund_full_hours` before the start → everything back; at least `refund_partial_hours` → that percent; later → nothing. Not approved yet (`pending`) or cancelled / rejected by the studio → everything back.
- `payment_code text not null unique` (migration `20261117000500_booking_payments.sql`): 'OOPS' + 6 characters, one namespace with `tuition_invoices.payment_code`; set by the server on insert and never changed (trigger `booking_payment_code`). It goes into the booking's VietQR transfer content ("OOPS7K3M9Q dat phong 12/11"). A transfer carrying it is matched to the booking: the amount is added to `bank_transfer`, `real_income` follows while it equals `bank_transfer + cash`, and `deposit_status` becomes `completed` once the deposit is covered (back to `waiting` when a taken-back transfer uncovers it). Due now = the rest of the deposit while it is `waiting`, then `full_payment − bank_transfer − cash`.
- `list_price numeric(12,0)`: the room's price × hours, recomputed when the room or the times change (trigger `booking_price`, which also fills `full_payment` and `deposit` = half on insert when not given). `full_payment` is the agreed price: it follows `list_price` until staff change it with `booking_set_price` (then `price_note` says why), and an open half deposit follows it.
- **booking_payment_entries**: money staff took by hand — `booking_id` (cascade), `method` (`cash` | `transfer`), `amount` (≠ 0; negative = refunded), `note`, `created_by`, `created_at`. Staff read; written only by `booking_record_payment` / `booking_delete_payment`. Amounts entered before this history get one line noted 'Recorded before payment history'. Together with the matched bank transfers it is the booking's payment history; money fields are no longer edited by hand in the UI.
- `details text`
- `created_at`, `updated_at`
- **Exclusion constraint** `bookings_no_overlap` (btree_gist): the same room cannot have two bookings with overlapping `[start, end)` ranges on the same date while status is `pending` or `approved`. Back-to-back bookings (10:00–12:00 then 12:00–13:00) are fine. Violations by direct writes surface as Postgres `23P01`.
- **Trigger** `check_booking_rules`, for `create_booking` **and** for staff writing the table directly:
  - `INVALID_INPUT: …` when the times break the rules above (so callers get the contract code rather than `23514`);
  - `SLOT_TAKEN: …` when a `pending`/`approved` booking overlaps a class scheduled in that room on `isodow(date)` (only while the class runs, `starts_on`…`ended_on`, and not on a day its session was cancelled — `private.class_holds_room`, migration `20261117000300_booking_free_slots.sql`) or a make-up session.
  - Reopening a cancelled session (status `cancelled` → anything else) whose slot was booked meanwhile is refused with `SLOT_TAKEN` (trigger `guard_session_reopen`).

**instructor_attendance** (legacy name: `Attendance`)
- `id bigint identity pk`

- `instructor_id uuid not null references profiles`

A cancelled weekly session gets no roll call; reopening today's brings it back.

**Views** use `security_invoker = true` so RLS still applies:
- `v_revenue_monthly`
  - Columns: `month date, room_id, room_name, bookings_count int, full_payment_sum, real_income_sum, cash_sum, bank_transfer_sum` (sums are `0`, never `null`)
  - Counts only bookings with status `approved` or `completed`, grouped by `date`'s calendar month.
  - Staff-only: rows are filtered by `is_staff()`, so a guest gets an empty result and anon gets permission denied.

**Tuition** (học phí; migrations `20261112000100_tuition.sql`, then **per course** since `20261116000100_course_tuition.sql` and `20261116000400_switch_after_course.sql`)
- **Per course (khoá):** a course is a routine (`class_lessons`, fee `price`, null = the class price). Invoices belong to a course: `lesson_id`, `lesson_title`, `sessions` (sessions covered), `month` = the month the course starts (reports count tuition there). One invoice per student and course (partial unique index `tuition_invoices_one_per_course`). Someone **new** joining after a course started pays for the sessions left (`prorate_late_join`), rounded to 1,000 ₫; members carrying on pay the whole course.
- **Renewal:** when the running course has `renewal_open_sessions` (default 2) or fewer sessions left and the next course is planned — or when nothing is running — every member is billed for the next course (`tuition_open_course` opens it at once). Pay or answer by the course's `due_session`-th session (default 2nd; at least 3 days after billing). Unpaid + unanswered + past due → `void` / `not_renewed`; a student whose invoice for the course their class is running is cancelled leaves the class. Students leaving mid-course get no refund.
- **Members over time:** `class_students.joined_at` may be in the future (joining from an upcoming course: that course is billed on enrolment; nothing earlier is) and `leaves_after` (they stay until that date, then the daily job removes them; courses starting after it aren't billed to them).
- **Class switch = between courses** (`tuition_switch_class`): the student joins the new class's first course starting today or later (billed in full; `joined_at` = its start) and finishes the running course in the old class (`leaves_after` = its last session). Invoices for the old class's later courses become `void` / `switched` and their money moves to the new course; the new course's invoice has `switched_from`. Reports count switches by `switched_from`.
- The monthly fields `invoice_day` / `due_day` and the description below of monthly billing are superseded by the rules above.

**Tuition (original monthly design, superseded where the per-course rules above differ)**
- Enums: `tuition_status` (`unpaid`, `paid`, `waived`, `void`), `tuition_renewal` (`continue`, `stop`), `payment_method` (`transfer`, `cash`).
- `tuition_settings`: one row (`id = 1`): `bank_code` (VietQR bank id: BIN such as `970436`, or a short name such as `VCB`), `bank_name`, `account_no`, `account_name` (all nullable until an admin fills them in), `invoice_day` (15–28, default 25: next month's invoices open), `due_day` (1–28, default 10: pay or answer by then).
- `tuition_invoices`: one per student × class × month (`unique (student_id, class_id, month)`).
  - `student_id` / `class_id` (`on delete set null`), plus `student_name` / `class_name` snapshots so deleting either keeps paid history (invoices that never had money on them are deleted with the class or person).
  - `month` (first day), `amount` (the class price when billed), `paid_amount` (partial payments add up), `status`, `renewal` (the student's answer for that month; null = no answer), `method`, `payment_code` (`OOPS` + 6 of `2-9A-HJ-NP-Z`, unique: goes in the transfer content), `due_date` (the month's `due_day`, at least 7 days after it was created), `paid_at`, `void_reason` (`stopped` | `not_renewed` | `removed` | `switched`, set exactly when `status = 'void'`), `switched_from` (on the new class's invoice after a class switch: the old one), `note`, `updated_by`.
  - **Lifecycle:** adding a student to a class bills the current month (`renewal = 'continue'`), and next month too from `invoice_day`. The daily job (§8) bills enrolments without an invoice, opens next month from `invoice_day`, voids (`not_renewed`) invoices that are unpaid, unanswered and past due, and removes from the class everyone whose current-month invoice is void. Removing a student voids their unpaid invoices from this month on (`removed`). Paying a `stopped` / `not_renewed` invoice of the current or next month reinstates it and puts the student back in the class.
- `bank_transfers.booking_id` (→ bookings, `set null`): the room booking a transfer paid, instead of an invoice; the matched transfers of a booking are its payment history.
- `bank_transfers`: money received on the studio account: `provider` (`sepay`, `demo`, …) + `provider_ref` (unique: a webhook delivered twice is stored once), `amount`, `content`, `received_at`, `status` (`matched` | `unmatched` | `ignored`), `invoice_id`, `note`, `raw`. A transfer is matched when its content contains an invoice code (case and separators ignored) whose invoice is unpaid; otherwise it waits as `unmatched` with a note.

- `tuition_extra_moves` (migration `20261117001200_tuition_extra.sql`): extra tuition money, i.e. a `paid` invoice holding more than its price (`paid_amount > amount`: a transfer bigger than the course, one put on the wrong course, a class switch). One row per move: `invoice_id` (→ tuition_invoices, cascade) the invoice it left, `kind` `moved` (onto `to_invoice`, → tuition_invoices, set null) or `refunded` (given back to the student: `method` cash / transfer, optional `note` ≤ 300), `amount` > 0, `created_by`, `created_at`. The invoice's `paid_amount` drops by each move, so the finance report counts only what the studio keeps. Rows are written by the RPCs only; staff can read them.
- `tuition_invoices.note_before_waive`: the note an invoice had before it was waived (the waive reason replaces `note`); `tuition_reopen` puts it back, so a reopened invoice no longer shows the waive reason.

**Expenses** (migration `20261113000100_switch_and_expenses.sql`): every cost that isn't payroll.
- Categories (`private.is_expense_category`): `rent`, `utilities`, `video` (camera crew, editing), `costumes`, `shoot_location`, `equipment`, `marketing`, `events`, `maintenance`, `supplies`, `venue_rent` (a rented studio's rent, added per session — see Rented studios), `other`.
- `expenses`: `spent_on date`, `month` (generated: first day of `spent_on`'s month), `category`, `amount > 0`, `description` (1–200), `vendor?`, `class_id?` (→ classes, `set null`: a cost that belongs to one class, e.g. its shoot's camera crew or costumes), `method?` (`payment_method`), `receipt_path?` (bucket `receipts`, §7), `recurring_id?`, `session_id?` (→ instructor_attendance, `set null`, unique: a rented studio's rent for that session), `created_by` (default `auth.uid()`; null = added by the system), timestamps. `unique (recurring_id, month)`.
- `recurring_expenses`: `category, amount, description, vendor?, class_id?, method?, day_of_month` (1–28), `starts_on` / `ends_on?` (first days of months), `active`, `created_by`. The daily job (§8) adds each active one on its day of every month in range.

**site_settings** (migration `20261117001500_timetable_templates.sql`): the website's choices, one row (`id = 1`, `check`).
- `timetable_template text not null default 'poster'`: the look of the public Classes page's weekly timetable — `poster` (the printed schedule's grid: days across, a round instructor photo per class on its level's colour) or `brush` (the first design: a red card, one column per day, brush-stroke badges).
- `updated_at`, `updated_by uuid` (→ profiles, `set null`).
- Everyone reads it (anon included, for the public page); nobody writes it directly: admins and staff change it with `site_set_timetable_template` (§5), from the Timetable view of the admin Classes page.

**activity_log** (migration `20261117000200_activity_log.sql`): who did what, for the admin's Activity page.
- `id`, `at timestamptz` (default now), `actor_id uuid` (null = the system: a job, the bank, a sign-up), `actor_name`, `actor_role` (as they were then), `area`, `action`, `entity` (table), `entity_id text`, `class_id`, `subject_id uuid` (the person the record is about), `label` (a guest, class, student or routine title, as it was), `meta jsonb` (facts for the sentence), `changes jsonb` (`{ column: { from, to } }` for edits). No foreign keys: it outlives what it mentions.
- Written by the trigger `zz_log_activity` (`private.log_activity()`) on bookings, classes, class_schedules, class_lessons, class_students, instructor_attendance, student_attendance, tuition_invoices, bank_transfers, expenses, recurring_expenses, payslips, payroll_adjustments, staff_salaries, class_pay_rates, payroll_settings, tuition_settings, rooms and profiles. The actor is `auth.uid()`. Generated rows (weekly sessions, roll calls, invoices) aren't logged, only what people change on them. Without a signed-in person only these are logged: a payment arriving (bank), an invoice cancelled (renewal cycle), a student leaving after their course, an unmatched transfer, an account created or deleted (`admin-users` then names the admin, §6). A failure inside the trigger only raises a warning. `set_config('oops.activity', 'off', true)` skips it for one transaction.
- Areas and actions: `bookings` (created, approved, rejected, cancelled, completed, reopened, payment_updated, updated, deleted) · `classes` (created, updated, ended, reopened, instructor_changed, deleted, schedule_added/changed/removed) · `routines` (planned, updated, deleted, video_added/changed/removed) · `students` (enrolled, removed, leaving, staying, updated) · `sessions` (checked_in, checked_out, approved = staff completing it, cancelled, reopened, substituted, note, make_up_added/removed) · `roll_call` (attended, absent, unmarked, note) · `tuition` (paid, payment_undone, waived, reopened, cancelled, amount_changed, renewal, note, transfer_unmatched/assigned/ignored/reopened) · `expenses` (created, updated, deleted, receipt_added/removed, recurring_created/updated/paused/resumed/deleted) · `payroll` (payslip_finalized/paid/unpaid/reopened, bonus_added, deduction_added, adjustment_changed/removed, salary_set/removed, rate_set/removed) · `rooms` (created, updated, photos_changed, deleted) · `users` (account_created, account_deleted, role_changed, profile_edited = someone else changed their details) · `settings` (updated, timetable_template = the website timetable's look, from `site_set_timetable_template`). The `meta` keys per action are listed in `frontend/src/services/activity.js`.
- RLS: admins select; nobody writes directly. Pruned after 400 days (§8).

## 4. RLS

RLS is enabled on every table and denies by default.

|---|---|---|---|---|---|
| profiles | — | select/update own (not role/email) | own + select students of own classes | select all, update non-role fields | all |
| rooms | select | select | select | CRUD | CRUD |
| venues | select (no rent, no note) | same | same | same; rent and writes via the venue RPCs | same as staff |
| classes, class_schedules, class_lessons | select | select | select | CRUD | CRUD |
| class_students | — | select own | select rows of own classes | CRUD | CRUD |
| payroll_settings, class_pay_rates, staff_salaries, payroll_adjustments | — | — | — | — | CRUD (settings: update) |
| payslips | — | — | — | — | select; writes via the payroll RPCs |
| tuition_settings | — | select | select | select | select, update |
| tuition_invoices | — | select own | — | select; writes via the tuition RPCs | same as staff |
| bank_transfers | — | — | — | select; writes via the tuition RPCs | same as staff |
| tuition_extra_moves | — | — | — | select; writes via `tuition_move_extra` / `tuition_refund_extra` | same as staff |
| expenses | — | — | — | CRUD on rows they created | CRUD |
| recurring_expenses | — | — | — | — | CRUD |
| bookings | — | select own; insert only via `create_booking`; cancel via `cancel_booking` | same as guest (for own bookings) | CRUD | CRUD |
| instructor_attendance | — | — | select own; writes only via RPC | CRUD | CRUD |

| activity_log | — | — | — | — | select (written by the trigger) |

- "—" for anon means the role has **no table privilege**: the request fails with `42501 permission denied` (HTTP 401), not an empty list.
- Writes blocked by RLS: `insert` fails with `42501 new row violates row-level security policy` (HTTP 403); `update`/`delete` silently affect 0 rows.
- Deleting a `profiles` row (admin) does not delete the auth user. Use the `admin-users` function to delete users.

The public homepage needs instructor names and avatars without exposing `profiles`, so it uses `list_public_classes()`.

## 5. RPC functions (`supabase.rpc(name, args)`)

Every function is `security definer` with `set search_path = ''` and performs its own role check.

**Public lookups**
- `get_available_slots(p_date date)`
  - Callers: anon and up.
  - Returns `table(room_id bigint, room_name text, start_time time, end_time time)`: merged free windows between 08:00 and 22:00 on a 30-minute grid, ordered by `room_id, start_time`.
  - Excludes `pending`/`approved` bookings, `class_schedules` (of classes in that room) where `day_of_week = isodow(p_date)` while the class runs and its session that day isn't cancelled, and make-up sessions. A class not on the grid (e.g. 19:45) blocks every half-hour slot it touches.
  - A past `p_date` returns no rows. For today, slots that have already started are dropped.
  - A room with no free time that day returns **no row** (list rooms separately if you need every room).
- `list_public_classes()` — `room_name` is the place's name (a room or a venue); `venue_address`, `venue_map_url` for a class at a venue.
  - Callers: anon and up.
  - Returns `table(id, name, price, lesson, image_path, room_name, instructor_name, instructor_avatar_path, schedules jsonb, venue_address, venue_map_url, place_kind, level, image_pos_x, image_pos_y, timetable_photo_path, timetable_photo_x, timetable_photo_y, timetable_photo_zoom)` ordered by `name`, where `schedules` = `[{day_of_week, start_time: "HH:MM:SS", end_time: "HH:MM:SS"}]` (`[]` when none), `place_kind` = `room` | `venue` (null when not set), `level` = the class's level (`newbie | basic | advanced`, null when not set; the poster timetable's colours) and the last six = how its pictures are framed (§3 classes: the card's crop of the image; the timetable photo, null = the instructor's avatar, and its frame).
- `is_username_available(p_username text)`
  - Callers: anon and up. Returns `boolean` (`false` for blank input). Use it on the sign-up form.

**Bookings**
- `create_booking(p_room_id bigint, p_date date, p_start time, p_end time, p_details text default null, p_guest_id uuid default null)`
  - Callers: authenticated users. `p_guest_id` (book on behalf of someone) is **staff only**; null means the caller.
  - `p_start` / `p_end` must be on the 30-minute grid (`HH:00` / `HH:30`).
  - Returns the new `bookings` row: status `pending` when a user books for themselves, **`approved`** when staff passes `p_guest_id`.
  - Amounts are computed on the server: `full_payment = rooms.price × hours`, `deposit = 50 % of full_payment` (rounded to whole VND). `real_income`, `cash`, `bank_transfer` stay `null` for staff to fill.
  - Errors:
    - `FORBIDDEN` not signed in, or a non-staff caller passes someone else's `p_guest_id`
    - `INVALID_INPUT` missing argument, `end <= start`, outside 08:00–22:00, or off the 30-minute grid
    - `PAST_DATE` date before today, or today with a start time already passed
    - `NOT_FOUND` unknown room or `p_guest_id`
    - `SLOT_TAKEN` overlaps a live booking or a class schedule
- `cancel_booking(p_booking_id bigint, p_by_studio boolean default false, p_refund numeric default null, p_note text default null, p_refund_to text default null)`
  - Callers: the owner while status is `pending` or `approved` and the booking hasn't started (`INVALID_STATE: the booking has already started`); staff while `pending` or `approved`.
  - The refund follows the policy (`booking_settings`); staff: `p_by_studio` = the studio cancels (everything back), `p_refund` overrides the amount (0 … paid) and then needs `p_note`. The guest's `p_refund_to` says where to send it. Guests' `p_refund` / `p_by_studio` are ignored.
  - Returns the `bookings` row (status `cancelled`, `refund_due`, `real_income` = what the studio keeps). Logged as `bookings · cancelled` with meta `refund, percent, tier, by_studio, note`.
  - Errors: `NOT_FOUND` (unknown id, or another user's booking — existence is not revealed), `INVALID_STATE` (wrong status, started), `INVALID_INPUT` (refund out of range / without a reason).

**Instructor attendance**

The proof photo must be uploaded **before** the RPC, to `attendance-proofs/{instructor_id}/{attendance_id}/{checkin|checkout}.{jpg|jpeg|png|webp}` (§7). `p_proof_path` is that object path (without the bucket name).
- `instructor_check_in(p_attendance_id bigint, p_proof_path text)`
  - Caller: the row's instructor, only on the row's date, from 15 minutes before the session starts until it ends (migration `20261117001100_checkin_window.sql`; the session's own times, else the class's weekly slot that day): `INVALID_STATE: check-in opens at HH:MM (15 minutes before the session)` / `INVALID_STATE: the session is over; ask the studio to record it`. The proof is checked first.
  - Status `pending`/`waiting` → `in_progress`. Sets `checkin_at = now()`.
  - Returns the `instructor_attendance` row.
  - Errors: `NOT_FOUND`, `FORBIDDEN` (another instructor's session), `INVALID_STATE` (wrong date or status), `INVALID_INPUT` (bad path or photo not uploaded).
- `instructor_check_out(p_attendance_id bigint, p_proof_path text)`
  - Caller: the same instructor (no date restriction, so a forgotten check-out can be done later).
  - Status `in_progress` → `completed`. Sets `checkout_at = now()`. Early is fine; more than 10 minutes after the session's end sets `checkout_late` (a badge for staff).
  - Returns the `instructor_attendance` row. Same error codes as check-in.
- `session_edit_check(p_attendance, p_checkin_at, p_checkout_at, p_checkout_late default null, p_reason)` (staff) → the row with corrected times: a reason is required; `p_checkout_at` null = not checked out (status `in_progress`), else `completed`; `p_checkout_late` null = worked out from the times, true / false = staff decide. Logged as `sessions · check_edited` with `changes` (each field from → to) and `meta.reason`.

**Attendance generation** (both idempotent; both returned counts are rows created, `0` = already generated)
- `generate_instructor_attendance(p_week_start date default null)`
  - Callers: staff, pg_cron and the service role.
  - `null` means the Monday of `studio_today()`; any other date is normalised to the Monday of its ISO week.
  - One row per (class, scheduled date): a class with two sessions on the same day gets one row.
  - Returns `int`.
- `generate_student_attendance(p_date date default null)`
  - Callers: staff, pg_cron and the service role.
  - `null` means `studio_today()`. One row per enrolled student of every class scheduled on `isodow(p_date)`; students whose `joined_at` is after `p_date` are skipped.
  - Returns `int`.

**Admin**
- `admin_set_role(p_user uuid, p_role app_role)`
  - Caller: admin.
  - Returns the `profiles` row.
  - Errors: `FORBIDDEN`, `NOT_FOUND`, `INVALID_STATE` (last admin / instructor who still teaches, see §2).

**Stats**
- `dashboard_stats()`
  - Caller: staff.
  - Returns `jsonb {monthly_booking_count, total_students, classes_today, revenue_this_month}`, month = current calendar month in studio time:
    - `monthly_booking_count`: bookings dated this month, excluding `cancelled`/`rejected`
    - `total_students`: distinct enrolled students (`class_students`)
    - `classes_today`: distinct classes with a schedule on today's ISO weekday
    - `revenue_this_month`: `sum(real_income)` of `approved`/`completed` bookings dated this month (same basis as `v_revenue_monthly.real_income_sum`)
- `my_stats()`
  - Caller: authenticated users.
  - Instructors get `{class_count, completed_sessions}`.
  - Everyone else (guest, staff, admin) gets `{class_count, attended_count, absent_count}`.

**Helper**
- `studio_today()`: callable by anyone, returns `date`.

**Errors**: functions `raise exception` with a stable code at the start of the message, e.g. `SLOT_TAKEN: …`. PostgREST returns them as HTTP 400 with body `{ "code": "P0001", "message": "SLOT_TAKEN: …" }`. The codes are:
- `FORBIDDEN`
- `NOT_FOUND`
- `INVALID_STATE`
- `INVALID_INPUT`
- `SLOT_TAKEN`
- `PAST_DATE`

**Payroll RPCs** (admin, or the service role for seed scripts; anyone else gets `FORBIDDEN`):
- `payroll_month(p_month date)` → one row per person to pay that month: `profile_id, full_name, username, email,
  avatar_path, updated_at, role, sessions, session_pay, base_salary, bonuses, deductions, total, status
  ('draft' | 'finalized' | 'paid'), finalized_at, paid_at`. Lists every instructor and staff member, plus anyone else
  with a salary, sessions, adjustments or a payslip that month. A finalized month returns its payslip's numbers.
- `payroll_finalize(p_profile uuid, p_month date)` → `payslips`: stores the live numbers; `INVALID_STATE` if already
  finalized. Any day of the month may be passed.
- `payroll_reopen(p_profile uuid, p_month date)`: deletes the payslip (back to draft); `INVALID_STATE` if not
  finalized or already paid.
- `payroll_set_paid(p_profile uuid, p_month date, p_paid boolean)` → `payslips`: `finalized → paid` (sets `paid_at`)
  or back; `INVALID_STATE` otherwise.

**Class lifecycle and routines RPCs** (staff; codes as above):
- `class_end(p_class, p_last_day date, p_reason)` → `{ class_id, ended_on, paid_after: [{invoice_id, student_id, student_name, month, paid_amount}] }`: the class runs until `p_last_day` (today or later); unpaid invoices for later months become `void` / `class_ended`, pending sessions and roll calls after it are deleted; `paid_after` lists students who already paid for a later month (switch or refund them). `class_reopen(p_class)` → `{ restored, skipped }` (schedule rows restored where the room is free). `classes_run_endings()` → classes wrapped up (the daily job).
- `lesson_progress(p_class_ids bigint[])` (any signed-in user) → per routine: `lesson_id, class_id, title, starts_on, session_count, sessions_held, sessions_cancelled, next_session, ends_on` (projected last session: weekly sessions + make-ups − cancelled), `status` (`planned` | `current` | `done` | `stopped`).
- `class_add_session(p_class, p_date, p_start time, p_end time, p_note)` → the new `instructor_attendance` row (`is_extra = true`, own `start_time` / `end_time`): a make-up session on a day the class doesn't meet (today or later, 08:00–22:00); `SLOT_TAKEN` against bookings, classes and other make-ups in the room; a roll call is created (now if today, else by the daily job); it blocks bookings and counts for payroll when completed. `lessons_refresh()` (the daily job).

**Tuition RPCs** (security definer; codes as above):
- Students (own invoices) and staff: `tuition_set_renewal(p_invoice bigint, p_decision tuition_renewal)` → the invoice. `stop` voids an unpaid month (`stopped`) and, for the running month, removes the student from the class now; next month's stop takes effect when it starts. `continue` records the answer, or reinstates a `stopped` / `not_renewed` month. `INVALID_STATE` for a past month or a paid one (stop).
- Staff (admin included): `tuition_mark_paid(p_invoice, p_method default 'cash', p_amount default <due>, p_note)` · `tuition_undo_payment(p_invoice)` (linked transfers go back to `unmatched`) · `tuition_waive(p_invoice, p_note)` · `tuition_reopen(p_invoice)` (waived → unpaid; void → reinstated) · `tuition_set_amount(p_invoice, p_amount, p_note)` (unpaid only) · `tuition_open_month(p_month)` (current or next month; returns how many invoices were created) · `tuition_assign_transfer(p_transfer, p_invoice)` · `tuition_ignore_transfer(p_transfer, p_ignore default true, p_note)` · `tuition_run_cycle()` (the daily job on demand → `{today, billed, opened, not_renewed, enrolments_ended}`).
- Staff, extra money: `tuition_extra_list()` → the invoices holding extra (newest payment first; RLS applies) · `tuition_move_extra(p_invoice, p_to_invoice, p_amount default <as much as fits>)` → the invoice paid: moves extra onto another **unpaid** invoice (any student's; the app offers the same student's courses) and pays it with the first invoice's method · `tuition_refund_extra(p_invoice, p_amount default <all of it>, p_method default 'cash', p_note)` → the invoice: records that the extra went back to the student. `INVALID_STATE` no extra / the other invoice isn't unpaid · `INVALID_INPUT` more than the extra, more than the other invoice still needs, ≤ 0, or the same invoice. Each logs one activity entry (`extra_moved`, `extra_refunded`). `tuition_undo_payment` now also takes moved extra back off the invoices it paid (`extra_move_undone`), returns extra moved in to where it came from, and is refused (`INVALID_STATE`) once part of the payment was given back.
- Staff: `tuition_switch_class(p_student uuid, p_from bigint, p_to bigint, p_note text)` → the invoice of the new class's upcoming course (see "Class switch" in §3: between courses, no refund). `INVALID_INPUT` same class · `INVALID_STATE` not in `p_from` / already in `p_to` / `p_to` has no upcoming course ("plan its next course first") · `NOT_FOUND` unknown class.
- Staff: `tuition_open_course(p_lesson bigint)` → invoices created: bills every member of the course's class for it now. `tuition_open_month(p_month)` opens every course starting in that month.
- Service role only: `tuition_record_transfer(p_provider, p_ref, p_amount, p_content, p_received_at, p_raw)` → `{transfer_id, status, invoice_id, note, duplicate}` (the bank webhook, §6).
- Sandbox: `tuition_sandbox()` → true on the hosted demo (`is_demo_instance()`) and the local stack (flag set by `seed.sql`). `tuition_simulate_transfer(p_invoice)` (the invoice's student or staff; sandbox only, else `FORBIDDEN`) records a fake `demo` transfer with the code and runs the same matching.
- `seed_demo_tuition()` (service role on a sandbox only): the demo data of §11. `tuition_waive` keeps the earlier note in `note_before_waive`; `tuition_reopen` of a waived invoice restores it.

**Booking payments** (security definer; migration `20261117000500_booking_payments.sql`):
- `booking_payments(p_booking)` (the booking's guest, staff; else `NOT_FOUND`) → its payments, oldest first: `kind` (`bank` = a matched bank transfer, `entry` = recorded by hand), `id, method, received_at, amount, content` (bank only), `note, recorded_by, recorded_by_name` (entries).
- Staff: `booking_record_payment(p_booking, p_amount, p_method default 'cash', p_note)` → the booking (money taken by hand; a negative amount is a refund and needs a note; not more than came in that way) · `booking_delete_payment(p_entry)` → the booking (the entry's money comes off) · `booking_set_price(p_booking, p_amount, p_note, p_deposit default null)` → the booking (a new agreed total; `INVALID_INPUT` without a note unless it is the list price; an open deposit becomes half, or `p_deposit`; a paid one stays, capped at the total). They log `paid` / `refunded` / `payment_removed` / `price_changed` in the activity log with the staff member as actor.
- Staff: `booking_staff_create(p_guest, p_room, p_date, p_start, p_end, p_details, p_status default 'approved', p_price, p_price_note, p_paid default 0, p_method default 'cash', p_payment_note)` → the booking, in one transaction: `create_booking` for the guest (status `approved`, or `pending` to hold it), then `booking_set_price` when `p_price` differs, then `booking_record_payment` when `p_paid > 0`. Same codes as those; nothing is booked when any step fails.
- Staff: `booking_assign_transfer(p_transfer, p_booking)` → the transfer (an unmatched or ignored one; `INVALID_STATE` when already matched or the booking is rejected / cancelled) · `booking_unassign_transfer(p_transfer)` → the transfer back in the inbox (`note` 'Taken back by staff.'), the money off the booking.
- Sandbox (`tuition_sandbox()`): `booking_simulate_transfer(p_booking, p_amount default <due now>)` (the guest or staff) → `{ transfer_id, status, booking_id, note }`; `INVALID_STATE` when nothing is due.
- The bank webhook (`tuition_record_transfer`) matches invoice codes first, then booking codes, and now also returns `booking_id`. A transfer for a rejected / cancelled booking stays `unmatched` with the note 'Booking #… is cancelled.'. A bank payment is logged as the system (`activity_log` area `bookings`, action `paid`).
- `tuition_set_note(p_invoice, p_note)` (staff; migration `20261117000600_invoice_notes.sql`) → the invoice with its note set ('' clears it), without changing anything else.
- `seed_demo_booking_payments()` (service role on a sandbox): approved bookings with a paid deposit received it by transfer, and every transferred amount gets its matched transfer.

**Session changes** (security definer; migration `20261117000900_session_changes.sql`):
- Staff: `session_cancel(p_class, p_date, p_reason)` → the session row, `cancelled` with its reason (required). Today or later; also a day ahead whose row doesn't exist yet (created as cancelled; `INVALID_STATE` when the class doesn't meet that day); not one that started or happened (`INVALID_STATE`). Unmarked roll calls that day go. Logged as `sessions · cancelled` with `meta.reason`.
- Staff: `session_move(p_class, p_date, p_new_date, p_start, p_end, p_reason)` → `{ cancelled, make_up }`: `session_cancel` then `class_add_session` (same rules and codes) on another day, the make-up's `makes_up` = `p_date`. Works for a session already called off (its make-up later). One transaction.
- Staff: `studio_close_day(p_date, p_reason, p_cancel_bookings default true)` → `{ sessions, bookings, classes: [{ class_id, name }] }`: every class session that day is called off; with `p_cancel_bookings` every pending / approved booking that day is cancelled by the studio (`cancel_booking … p_by_studio`, everything paid due back). Logged as `sessions · day_closed` (entity `studio`, entity_id the date).
- `my_session_changes(p_days default 21)` (any signed-in person) → `id, class_id, class_name, date, kind ('cancelled' | 'make_up'), start_time, end_time, reason, makes_up, room_name` (the place: a room's or a venue's name): changes from today to `p_days` ahead in classes the caller is in that day (member) or teaches.
- **Venues** (staff, admin included): `venues_list()` → every venue with its rent (active first) · `venue_save(p_id bigint|null, p_name, p_address, p_map_url, p_rent numeric, p_note, p_active boolean)` → the venue (null id adds one; `INVALID_INPUT` for an empty / duplicate name (any case), a non-https map link, a negative rent; `NOT_FOUND`) · `venue_delete(p_id)` (`INVALID_STATE` once classes were taught there: set it inactive instead) · `venue_rent_run()` → how many sessions' rent was charged (also the daily job). Each save / removal is one activity entry (area `rooms`, entity `venues`: `venue_added`, `venue_changed` with `changes`, `venue_removed`).

**Booking refunds** (security definer; migration `20261117000800_booking_refunds.sql`):
- `booking_cancel_quote(p_booking, p_by_studio default false)` (the guest's own booking, or staff) → `{ received, percent, refund, keep, hours_before, tier: 'full' | 'partial' | 'none' | 'pending' | 'studio', full_hours, partial_hours, partial_percent }` — what cancelling now gives back.
- Staff: `booking_refund(p_booking, p_method default 'transfer', p_note)` → the booking: the refund was paid back (`refund_due` → `refund_paid`, `refunded_at`; a negative payment entry 'Refund after cancellation'; the money leaves the chosen way first). `INVALID_STATE` when nothing is due. Logged as `refunded`.
- Staff: `booking_set_refund(p_booking, p_amount, p_note)` → the booking with a new `refund_due` (0 … paid; cancelled or rejected bookings; a reason is required). Logged as `refund_changed`.
- Admin: `booking_set_refund_policy(p_full_hours, p_partial_hours, p_partial_percent)` → `booking_settings`. Hours 1–720 (the full step more than the partial one), percent 0–100. Logged as `bookings · refund_policy`.

**Routine promos** (security definer):
- `lesson_set_promo(p_lesson bigint, p_path text default null, p_poster text default null, p_caption text default null, p_seconds integer default null, p_url text default null) → text[]`: staff or the class's instructor (else `FORBIDDEN`). Sets the routine's promo to the uploaded clip `p_path` (with poster and length; the files must already be in `class-promos` under `{class_id}/{lesson_id}/`, else `INVALID_INPUT: upload the clip before attaching it` / `…is stored under …`) or to the YouTube link `p_url` (else `INVALID_INPUT: a promo link is a YouTube video or Short`); both → `INVALID_INPUT: a promo is an uploaded clip or a YouTube link, not both`; neither takes the promo off. The same clip or link as now only changes the caption (a null poster / length keeps the current one). Also clears the promos of the class's finished routines (started before the running one). Returns the storage paths nothing points at any more (replaced clip and poster, finished routines' files): the app deletes them through the Storage API. Logs `routines` · `promo_added` / `promo_changed` / `promo_caption` / `promo_removed` (meta: class, starts_on, seconds, caption, youtube) instead of a routine edit.

**Website** (security definer; migration `20261117001500_timetable_templates.sql`):
- `site_set_timetable_template(p_template text)` (admins and staff, or the service role; else `FORBIDDEN`) → the `site_settings` row. `p_template` is `poster` or `brush` (else `INVALID_INPUT`); picking the look in use changes and logs nothing. Logged as `settings · timetable_template` (entity `site_settings`, label 'Website', meta `{ template, from }`).

**Activity log** (security definer):
- `activity_summary(p_from timestamptz, p_to timestamptz)` (admin; else `FORBIDDEN`) → `{ total, people: [{actor_id, name, role, count}], areas: [{area, count}], actions: [{area, action, count}] }` for the period (`p_to` exclusive). The feed itself is read from the table (`order=at.desc,id.desc`, filters on `actor_id`, `area`, `action`, `class_id`, `subject_id`, `label`).
- Service role: `activity_prune()` (the nightly job) · `seed_demo_activity()` (sandbox only: replaces the log with ~10 days made from the demo data) · `seed_demo_fit_routines()` (sandbox only: past demo routines last as many sessions as their month held, so they don't overlap).

**Finance report** (admin, or the service role; anyone else gets `FORBIDDEN`):
- `finance_monthly(p_from date, p_to date)` → one row per month (≤ 36, oldest first): `month, tuition_billed` (unpaid + paid invoices), `tuition_collected` (money received on that month's invoices), `tuition_outstanding, tuition_waived, transfer_amount, cash_amount, bookings_revenue` (`real_income` of approved/completed bookings dated that month), `payroll_cost` (sum of `payroll_month(month).total`), `expenses_total` (expenses spent that month), `costs_total` (= payroll + expenses), `revenue` (= collected + bookings), `profit` (= revenue − costs), per person: `students_active, students_new` (first month ever), `students_continuing` (also active the month before), `students_returning` (back after a break), `students_left` (active the month before, not this one); per class membership: `enrolments_active, enrolments_new, enrolments_renewed, enrolments_ended` (switches excluded), `class_switches`, `invoices_overdue`.
- `finance_by_class(p_month date)` → `class_id, class_name, instructor_name, students, billed, collected, outstanding, sessions` (completed that month), `instructor_pay` (sessions × class rate or default), `direct_costs` (expenses tied to the class that month), `margin` (= collected − instructor_pay − direct_costs). Shared costs are not split per class.
- `finance_expenses(p_from date, p_to date)` → `month, category, amount, items`.
- Admin (or service role): `expenses_run_recurring()` → how many recurring expenses were added for this month (the daily job on demand).

Postgres codes the frontend may also see from direct table writes: `42501` (no privilege / RLS insert violation), `23505` (unique), `23P01` (booking overlap → treat as `SLOT_TAKEN`), `23503` (row still referenced, e.g. deleting a room that has bookings), `23514` (check constraint).

The frontend maps these codes to UI messages.

## 6. Edge Functions

- **`admin-users`** (POST, `supabase.functions.invoke('admin-users', { body })`)
  - Verifies the caller's JWT with GoTrue and checks `profiles.role = 'admin'` server-side (`verify_jwt = false` at the gateway; the function does the check itself).
  - Actions:
    - `{action:"create", email, password, full_name, role, contact_number?, date_of_birth?}` → creates a confirmed user (password ≥ 8 chars, `date_of_birth` as `YYYY-MM-DD`) and sets the role.
    - `{action:"update", user_id, email}` → changes another user's login email immediately (no confirmation mail); `profiles.email` follows via trigger.
    - `{action:"delete", user_id}` → deletes the auth user (profile cascades).
  - Success: `200 { ok: true, user: <profiles row> }` for create/update, `200 { ok: true, user_id }` for delete.
  - Failure: `{ error: "CODE: message", code: "CODE" }` with the RPC code prefixes plus `INTERNAL`:
    - `401 FORBIDDEN` missing/invalid token · `403 FORBIDDEN` not an admin
    - `400 INVALID_INPUT` bad body · `404 NOT_FOUND` unknown user
    - `409 INVALID_STATE` email already used; deleting yourself; deleting a user who still has classes, bookings, teaching sessions or payslips (the message lists the counts; payslips would otherwise cascade away)
    - `500 INTERNAL`
  - Uses the service role internally. This is only needed because auth users can only be created, re-emailed or deleted with the service role.
  - Activity log: after a create or delete it names the calling admin on the `account_created` / `account_deleted` row the trigger wrote as the system, and logs an email change as `profile_edited` (best effort: a failure here doesn't fail the request).
  - **Demo mode:** when the function secret `DEMO_MODE` is `true`, `update` and `delete` on an `@demo.oopsdance.test` account return `403 { error: "FORBIDDEN: demo account", code: "FORBIDDEN" }`. `create` and accounts on other domains are unaffected.
  - CORS: `*` unless the function secret `ALLOWED_ORIGINS` (comma-separated origins) is set; then only those origins plus `http://localhost:5173` and `http://127.0.0.1:5173` are allowed. The public demo sets it to its Vercel domain.
- **`bank-webhook`** (POST, called by the bank-sync service SePay — not by the frontend)
  - `verify_jwt = false`; authenticates with the API key in `Authorization: Apikey <key>` (or `Bearer` / `x-api-key`), compared with the function secret `BANK_WEBHOOK_KEY`. No secret → `503`; wrong key → `401`.
  - Body (SePay): `{ id, gateway, transactionDate: "YYYY-MM-DD HH:mm:ss" (Vietnam time), accountNumber, content, transferType: "in" | "out", transferAmount, referenceCode, description }`. Money out is acknowledged and ignored.
  - Calls `tuition_record_transfer('sepay', id, transferAmount, content + description, …)`; replies `200 { success: true, status, invoice_id, duplicate }` (SePay retries anything else); errors `{ success: false, error: "CODE: message" }`.
  - Set up: SePay → Webhooks → URL `https://<project>.supabase.co/functions/v1/bank-webhook`, authentication "API Key"; then `supabase secrets set BANK_WEBHOOK_KEY=<the same key>`.
- Any additional function must be documented here.

## 7. Storage buckets

| bucket | public | path | write | read |
|---|---|---|---|---|
| avatars | yes | `{user_id}/avatar.{ext}` | owner (anything under `{user_id}/`) | public |
| class-images | yes | `{class_id}/{uuid}.{ext}`: the class image (`classes.image_path`) and its timetable photo (`classes.timetable_photo_path`) | staff | public |
| attendance-proofs | **no** | `{instructor_id}/{attendance_id}/{checkin\|checkout}.{jpg\|jpeg\|png\|webp}` | owning instructor, only while the session is in that phase | owner + staff (signed URL) |
| receipts | **no** | `{expense_id}/{file}` | whoever can see the expense (admin; staff for their own) | same (signed URL) |
| class-promos | yes | `{class_id}/{lesson_id}/{name}.{mp4\|mov\|webm\|jpg\|webp}` (name: letters, digits, `-`) | staff, and the class's instructor (`private.can_write_class_promo`) | public |
| site-assets | yes | `rooms/{room_id}/{file}` for room photos (listed in `rooms.image_paths`); otherwise free-form (homepage images/video) | staff / dashboard | public |

- Image buckets: max 5 MB, MIME `image/jpeg, image/png, image/webp`. HEIC is converted to JPEG on the client.
- `site-assets`: max 50 MB, MIME `image/jpeg, image/png, image/webp, image/gif, video/mp4, video/webm` (no SVG).
- `class-promos`: max 50 MB, MIME `video/mp4, video/quicktime, video/webm, image/jpeg, image/webp`. The app uploads the clip (with progress: a plain `POST /storage/v1/object/class-promos/{path}`), its poster frame, then calls `lesson_set_promo`; it deletes what the RPC hands back. Select/delete use the same rule as write (the Storage API needs both to remove).
- Room photos: upload to `site-assets/rooms/{room_id}/…`, then save the ordered list of paths in `rooms.image_paths`. Removing a photo = delete the object and drop it from the array.
- `attendance-proofs` write rule: `checkin.*` only while the row is `pending`/`waiting`, `checkout.*` only while it is `in_progress`; upload with `upsert: true` is fine until then. After the RPC the proof can no longer be replaced. Only staff can delete proofs.
- Public files: the frontend uses `getPublicUrl(path)`.
- Private files: the frontend uses `createSignedUrl(path, 3600)`.
